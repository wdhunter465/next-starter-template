# PMO Project-to-Cursor Delivery Promotion Decision Brief (#2872 / #4209)

## Purpose

Answer #4209's exact question: is the #2546 PMO Project-to-Cursor Autonomous Delivery
component still needed given the current live `lgfc-cursor-dispatch` / Chromebook runner
as-built, or has it been superseded? Render one of the three outcomes #2872 itself
authorizes: **keep**, **subset**, or **not-planned**.

This document makes **no Production promotion**, does not reopen #2546, and does not merge
`component/pmo-project-autonomous-delivery`. It is a docs-only deliverable at
`docs/ops/reports/pmo-cursor-delivery-promotion-decision-brief.md`, per #4209's declared
writable-file scope.

## What #2546 delivered

Per #2546's own closeout record (completed 2026-07-25, component branch
`component/pmo-project-autonomous-delivery`, closeout merge `0092c9bc` via PR #2624):

1. a canonical PMO project-delivery authority record;
2. a machine-readable **manifest contract and validator**;
3. an **idempotent task-Issue materializer** (turns a manifest into GitHub task Issues);
4. changed-manifest event selection and branch-safety behavior;
5. least-privilege workflow permissions for that materializer;
6. PMO portfolio migration evidence;
7. non-production component integration;
8. operator validation/dry-run/disable/recovery/rollback procedures;
9. final promotion metadata, with Production promotion explicitly withheld.

The component's core capability is **manifest-in, task-Issues-out**: an operator or PMO
authors a manifest file, and a validator + materializer turn it into the actual GitHub task
Issues for a project, idempotently. It was never merged past its own component branch —
Production promotion was deferred to this project (#2872) from the start.

## Current live as-built (verified 2026-09-21)

Per `docs/governance/standards/CURSOR-RUNTIME-ROUTING.md` (binding) and this session's own
direct verification:

- **Primary local Cursor transport** is `lgfc-cursor-dispatch` on the dedicated `lgfc-cursor`
  Chromebook runner, invoking `scripts/lgfc-cursor-dispatch/dispatch.mjs`. Eligibility is
  `agent:cursor` + `handoff:ready` labels on an open issue — no comment-marker protocol, no
  manifest file.
- **Cursor Local Bridge is decommissioned** (#3424); the historical wake-packet/poll-wake
  paths are retired execution dependencies.
- A repository-wide search of `scripts/` and `.github/workflows/` on current `main` finds
  **zero references** to `lgfc-project-manifest`, and no materializer or manifest-validator
  script exists outside the (unmerged) component branch. The manifest/materializer system
  #2546 built has never run against live `main`.
- Every currently active PMO project Issue this session inspected (#4089, #2872 itself,
  #3234, #3162, #3161, #3160, #2815, #2460, #2459, #2443, #4135) is a **manually-authored**
  GitHub Issue carrying hand-written `pmo-admin-current-state`/launch-package HTML-comment
  metadata blocks — not an artifact generated by a manifest materializer.
- The dispatch pipeline itself was independently verified end-to-end today: a stale-lock
  defect in `dispatch.mjs` (#4283) was found, fixed, and merged (#4284); a subsequent
  label-triggered wake was confirmed to reclaim the lock cleanly and invoke the authenticated
  local Cursor CLI, which posted its own confirmation comments and closed its test Issues
  without a human relaying any prompt (#4287, #4289).

## Analysis

#2546 addressed two related but separable problems: (a) *how does a task Issue come to
exist* (manifest → materializer), and (b) *how does Cursor get invoked to work it* (wake
delivery). Problem (b) is now solved by a different, independently-built and independently-
verified system (`lgfc-cursor-dispatch`, #3212/#3424) that has no dependency on #2546's
manifest contract at all. Problem (a) — the manifest-driven materializer itself — has no
live adoption: two months after completion, every active project continues to be authored
by hand, and no workflow or script on `main` references the manifest format at all.

There is no evidenced current pain point that a manifest-driven materializer would solve
today. Promoting a two-month-dormant component would also require revalidating it against
governance/CI machinery that has materially evolved since July (`reviewer_lifecycle_gate.mjs`
and its preparer-handback, `pr_hygiene_audit.mjs` hard-failure codes, `diff_scope_gate.mjs`,
the PR-body auto-repair scaffold) — none of which existed in current form when the component
was built, and none of which the component was ever validated against.

## Recommendation

**NOT-PLANNED.** Close #2872 on this basis:

- The invocation half of #2546's original problem is already solved, live, and verified by
  `lgfc-cursor-dispatch` — no gap remains for a promoted component to fill there.
- The materializer half has zero demonstrated need after two months of exclusively
  manual PMO issue authorship across every active project in the portfolio.
- Re-validating a dormant component against today's substantially-changed CI/governance
  surface, for a capability nothing currently asks for, is cost without an offsetting benefit.

This is a **keep-as-evidence** disposition, not a deletion: `component/pmo-project-autonomous-
delivery` and PR #2624 remain untouched, exactly as #2872's own non-goals require. If a
concrete future need for manifest-driven task materialization is identified, it should be
raised as a new, separately authorized project that revalidates against the CI/governance
surface current at that time — not a reopening of #2546 or a reuse of this brief as standing
authorization.
